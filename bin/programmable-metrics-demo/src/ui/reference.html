The model

A program is the whole metrics path after the sources, written as streaming queries in the style of Unix pipes: metrics enter as streams, flow through stages joined by |, and every path ends in a sink that delivers them or discards them.

It is one policy metrics { ... } block of statements. Statements are equations over streams, not steps in time: their order matters only in that a name is defined before it is used. Whitespace and line breaks do not matter, and # starts a comment that runs to the end of the line.

The quickest start is the editor's Load default program, which shows what ADP runs now, with comments, and changing it. Compiling shows every problem at its place in the text, and what would change.

Predicates

        
What a where (or a split) tests. The string tests are ==,
          !=, starts_with, and in [...], with starts_with [...] for
          several prefixes; they apply to name, intake_name, host,
          tags.<key>, and origin_tags.<key>. not binds tightest,
          then and, then or, and a junction of any length is written with and
          and or. Each predicate has one printed spelling.

Operators

        
Every stage names one of these. A parameter marked config may also read one of the
          bindings a program may read with config.<name>;
          positional marks the one that may be passed first without its name, and
          optional one that may be left out, its default shown where it has one.

        

        

      


      

        
Node IDs

        
Every stage and sink is a node of the plan, and every node has an ID, which the syntax derives from where
          it is written. The last stage of a let takes the let's name, so if something
          needs a specific name, give it one with let: let to_team_b = metrics | where
          tags.team == "b" names the filter to_team_b, and its sink, in
          to_team_b | emit "http://127.0.0.1:17102", is to_team_b_true. An
          as <id> clause after a stage or a sink names that node instead, for the rare cases a
          let cannot: a sink, which has an ID of its own, or a node named like a scope input.

        

          
Why IDs matter. ADP keeps a node's state, such as an aggregation's open buckets, and
            reuses its kernel from one program to the next by its ID. An edit that changes the ID of a node with state
            starts that state over. The editor warns when an edit renames one, and says how to keep its ID: name it with
            let.

WhereID

              x_<operator> (a where is x_split; a tuple head is
              x_in); a repeated operator takes _2, _3, ... in order.

              where the anchor is the port the pipeline starts from: a node's ID; x_<port> for
              x.port; input_<name> for a scope input; for a tuple head, its merge,
              <anchor of its first element>_in.

            
A stream used more than onceThe tee that copies it is x_fanout, or
              x_<port>_fanout after x.port; use i starts from
              <tee>_<i>.

            
A sink<node>_<port>, after the node and port it ends:
              where's drop is <split>_false.

Rules

        
The syntax enforces

        
Each of these is checked as the text is parsed, at the point where it is written:

        
    
          
  • Define before use. A let is visible only after its statement, and cannot
            refer to itself, so a cycle cannot be written.
    • 
          
  • Every stream and port is used. An unused let, or an unused port of a node
            with several, is an error, not a silent drop: write x.passthrough | drop to drop one.
    • 
          
  • A node with several output ports is never used bare: pick a port, as
            x.default.
    • 
          
  • Sinks end pipelines. To copy a stream, name it with let and use it twice.
    • 
          
  • A statement without let ends in a sink, and a let does not.
    • 
          
  • Names are unique. A let cannot reuse a scope input's name, another
            let's, or a node ID.
    • 
        

        
Compiling checks

        
Beyond the grammar. An error refuses the program; a
          warning lets it through. The rules marked
          met by the syntax hold for any text that parses; validation still checks them,
          for artifacts written as JSON.

Recipes

        
Common needs, each one line added to the default program: a stage at the end of the stream every
          destination reads, let metrics = ..., so that every use of metrics, one per
          destination, reads what it passes. Load the default program, add the line, and compile. Where enrichment
          does nothing, as in this demo, let metrics only names the stream it would have read,
          let metrics = dsd_post_agg_filter, and the line goes after it all the same.
