Scraping internal telemetry ​

Agent Data Plane exposes internal telemetry as OpenMetrics text on the unprivileged API endpoint. You can scrape this endpoint to collect ADP process, pipeline, and component metrics.

Endpoints ​

ADP serves its full internal telemetry at /metrics on data_plane.api_listen_address, also called the "unprivileged API address." The default address uses port 5100, so a default local scrape target is:

text
http://127.0.0.1:5100/metrics

This is an ADP-local endpoint. When ADP registers with the Core Agent, the Core Agent also exposes ADP series on its own /telemetry endpoint alongside Core Agent series. Prefer the Core Agent endpoint when you want a combined view; use ADP's /metrics endpoint when you want ADP telemetry only. ADP series on the Core Agent endpoint carry an emitter label so you can distinguish them from Core Agent series.

NOTE

The Core Agent serves /telemetry even when telemetry.enabled is false. Enabling that key adds other Core Agent telemetry; it is not a prerequisite for the combined scrape. ADP ignores the key and registers its local /metrics route independently.

Configure a scrape ​

For ADP-only telemetry, target its unprivileged API address. For the combined view, use http://localhost:5000/telemetry when your scraper runs on the Core Agent host. The Core Agent's expvar server listens on loopback at port 5000 by default; if you change expvar_port, update the port in your scrape target. These examples assume the scraper can reach that loopback listener.

Datadog Agent OpenMetrics check ​

To scrape ADP-only telemetry with the Datadog Agent, configure the OpenMetrics check with ADP's telemetry endpoint. To collect both Core Agent and ADP series in one scrape, target the Core Agent's /telemetry endpoint instead.

yaml
instances:
  - openmetrics_endpoint: http://127.0.0.1:5100/metrics
    namespace: agent_data_plane
    metrics:
      - ".*"

For a combined Core Agent and ADP scrape, use the Core Agent's telemetry listener rather than data_plane.api_listen_address:

yaml
instances:
  - openmetrics_endpoint: http://localhost:5000/telemetry
    namespace: datadog_agent
    metrics:
      - "dogstatsd__processed"
      - "transactions__.*"
      - "aggregator__flush"

Use narrower metric patterns when you do not need the full Core Agent telemetry surface. The metric names in this guide are exposition names; the OpenMetrics check may prefix submitted Datadog metric names with the configured namespace.

NOTE

The OpenMetrics check submits collected series as custom metrics. Use explicit metric names or narrower patterns when you do not need the full ADP telemetry surface.

Prometheus ​

For Prometheus-style scraping, use ADP's unprivileged API address for ADP-only telemetry. To collect the combined Core Agent and ADP view, use the Core Agent telemetry listener and set metrics_path to /telemetry instead.

yaml
scrape_configs:
  - job_name: agent-data-plane
    metrics_path: /metrics
    static_configs:
      - targets:
          - 127.0.0.1:5100

To scrape the combined Core Agent and ADP view instead, target the Core Agent telemetry listener:

yaml
scrape_configs:
  - job_name: core-agent-telemetry
    metrics_path: /telemetry
    static_configs:
      - targets:
          - localhost:5000

If you change data_plane.api_listen_address, update the ADP-local scrape target to match the configured host and port.

Migrate legacy expvar consumers ​

  1. Identify the expvar path your dashboard or go_expvar check reads from the Core Agent's /debug/vars endpoint. Do not substitute an entire metric family for a path that selects labels.
  2. Use the table below to find the corresponding ADP series on the Core Agent's /telemetry endpoint. Select the listed labels and keep emitter separate when comparing ADP and local traffic. Use counter rates for dashboards rather than adding raw counter values across restarts.
  3. If you rely on the existing expvar path, deploy a Core Agent version with the ADP expvar bridge. The bridge is a separate Core Agent change; Saluki's RAR remappings alone do not update /debug/vars. Until that change is available, query /telemetry directly for ADP values.

The Core Agent's /telemetry endpoint includes ADP series alongside local Agent series. The bridge combines ADP and local values only for its explicit mappings; a metric on /telemetry does not automatically become an expvar. The table shows the legacy paths and RAR metric families used by the proposed bridge, including known gaps. Paths below are relative to /debug/vars. The mappings identify series and selectors, not a guarantee that the two processes count every event at the same stage.

Contexts grouped by origin ​

Set telemetry.dogstatsd_origin: true to emit aggregator__dogstatsd_contexts_by_origin on /telemetry. The default is false. This gauge groups active DogStatsD contexts by their complete resolved origin-tag set. Contexts without resolved origin tags are omitted, so the gauge stays empty unless dogstatsd_origin_detection is also enabled. It is not a legacy expvar and does not replace aggregator/DogstatsdContexts.

The gauge exports up to 199 distinct origin groups and one origin_overflow="true" group for additional sets or sets exceeding 32 tags or 4096 bytes of encoded labels. Groups keep their assignment until their contexts expire, so an origin's own series is too low while the overflow group holds some of its contexts. Check the overflow group when comparing per-origin counts against the total. An emptied group reports 0 briefly before its series is removed.

Each tag key becomes one label. Keys that aren't valid Prometheus label names, or that clash with labels ADP adds, use the reversible Prometheus U__ escaping: for example, git.commit.sha becomes U__git_2e_commit_2e_sha. A key with several values gets one label that lists them sorted and comma-separated, such as kube_service="api,worker", with commas and backslashes inside a value escaped by a backslash. Bare tags and tags with empty values are listed in the origin_bare_tags label. ADP escapes special characters in label values according to Prometheus text exposition rules.

The six processed-message expvar metrics share dogstatsd__processed, so select both labels when querying /telemetry. For example, metric packets use message_type="metrics" and state="ok":

promql
sum(
  rate(dogstatsd__processed{emitter="Agent Data Plane",message_type="metrics",state="ok"}[5m])
)

Change state to error to query metric parse errors. The emitter value is the registered display name; replace Agent Data Plane if your deployment uses another name.

To combine the compatible series-flush counters, calculate the rate for each emitter before aggregating so counter resets remain visible:

promql
sum without (emitter) (rate(aggregator__flush{data_type="series"}[5m]))

Troubleshooting ​

If scraping fails, verify that ADP is listening on the unprivileged API address:

shell
curl http://127.0.0.1:5100/metrics

If you configured a non-default data_plane.api_listen_address, use that address instead of 127.0.0.1:5100.

If the endpoint returns data but dashboards do not populate, check whether the dashboard expects ADP-native names from /metrics or RAR names from the Core Agent's /telemetry endpoint.

If you are investigating DogStatsD-specific counters, the internal telemetry endpoint includes aggregate DogStatsD counters such as processed message counts, packet and byte counts, packet pool usage, and channel latency. This is separate from the on-demand DogStatsD statistics API documented in Agent Data Plane configuration.
